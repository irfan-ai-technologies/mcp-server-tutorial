Part 0 — Orientation · Chapter 2

The protocol in one chapter

The 2026-07-28 wire format read directly: stateless core, server/discover, _meta conventions, resultType, MRTR, Streamable HTTP.

Status draftProtocol 2026-07-28

You can read the entire MCP specification in an afternoon, and you should eventually. This chapter is the shorter route: every message that matters, shown as it actually travelled, with a server on the other end that you can run yourself.

Everything below was captured by code/labs/wire/capture.sh, which starts ledger and sends plain curl requests. The transcripts are committed to the repository. That is deliberate — when a library or the specification moves, re-running the script produces a diff, and the diff is what tells you the chapter needs revising.

Why curl and not a client library

A client library would hide the exact thing this chapter is about. There is no session here, no handshake, and no state carried between any two of these requests. That is easy to assert and hard to believe until you have watched it work.

The shape of every message#

MCP is JSON-RPC 2.0. A request has jsonrpc, an id, a method, and usually params. A response echoes the id and carries either result or error. If you have implemented JSON-RPC before, you already know the frame; what is specific to MCP is the method vocabulary and the _meta conventions.

Three things are absent and all three used to be mandatory. There is no Mcp-Session-Id header. There was no initialize call before this one. There is nothing tying this request to any earlier request — it is the first thing this client has ever said to this server, and it works.

Specification 2026-07-28

Sessions and the initialize/notifications/initialized handshake were removed. Every request carries its own protocol version and client capabilities in _meta — io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities — and clients SHOULD identify themselves per request with io.modelcontextprotocol/clientInfo. A version the server cannot speak comes back as UnsupportedProtocolVersionError.

This is the single most consequential change in the revision, and chapters 11 and 12 are about living with it. For now, notice only what it buys: any instance can answer any request, so the server behind that URL can be four processes behind a load balancer that have never heard of each other.

Read that as a prompt fragment, because that is what it is. The model sees the name, the description, the parameter names, the parameter descriptions, and the JSON Schema types. It does not see your implementation, your comments, or your intent.

Two details are worth pausing on. First, the description is "Licences attached to a title." — one line, even though the Python docstring is longer. FastMCP takes the first line as the tool description and lifts the Args: section into per-parameter descriptions. That is a sensible convention and it means the first line of your docstring is doing more work than you think.

Second, look at the outputSchema. The tool returns a list, and JSON Schema requires an object at the top, so FastMCP has wrapped it: {"result": [...]}, flagged with x-fastmcp-wrap-result. Your return type is not always the shape on the wire. Chapter 10 has opinions about this.

Results, and the field that should be there#

A result carries content — a list of content blocks, here one text block containing serialised JSON — and, since 2025-06-18, structuredContent, which is the same data as an actual object. Most clients will use the structured form when it is present and fall back to the text.

Now the part that is missing.

Specification 2026-07-28

All results carry a required resultType field: "complete" for an ordinary result, "input_required" for the interim result of a multi round-trip request. Clients MUST treat a result from an earlier-protocol server that omits the field as "complete".

There is no resultType in that response. FastMCP 4.0.3 does not emit one, and it does not emit ttlMs or cacheScope on list results either, both of which the revision requires. The specification anticipated servers like this — that is what the "treat a missing field as complete" rule is for — but it is worth being clear about what you are shipping. A server built on the library as it stands today is not fully conformant with the revision it claims to target.

The last clause of that rule is the interesting one. resultType exists to distinguish a finished answer from a server saying I need more from you. Which brings us to the mechanism it was added for.

Multi round-trip requests#

Older MCP let a server send requests back at the client mid-call: ask the client's model to sample something, ask the user a question, ask for the list of roots. That required a bidirectional, stateful connection, which is precisely what the revision set out to remove.

The replacement inverts it. A server that needs more information returns a result with resultType: "input_required" and an inputRequests field describing what it needs. The client gathers the answers and retries the original request, attaching inputResponses. Nothing is held open in between.

The consequence for design is that a server which needs a second piece of information must be able to reconstruct its position from the retried request alone. There is no "where we were" to resume. If your call has expensive state behind it, you encode a handle into requestState and hand it back — which is the same technique chapter 12 uses for everything else.

The method your server does not implement#

Ask ledger to describe itself:

server/discover is how a client learns which protocol versions a server speaks, what it is capable of, and who it is — before sending anything else. The specification says servers MUST implement it. FastMCP 4.0.3 answers "Method not found".

This is not a scandal. Every SDK is mid-migration through the largest revision the protocol has had, and FastMCP is moving faster than most. It is, however, exactly the class of fact you cannot learn from a release note, and the reason this chapter is built out of captured responses. When you need to know what your server does, send it a request. docs/protocol-notes.md in this repository tracks what was true when, and re-running capture.sh is how you find out what changed.

Resources and prompts on the wire#

Both are simpler than tools. resources/list returns URIs with metadata; resources/read returns contents. Here is an agreement:

Note what this resource returns for its children: URIs, not contents. It hands back enough to decide where to go next and no more. That habit is worth forming early — it is the entire technique of chapter 21, applied to a corpus far too large to read.

Prompts are text templates with typed arguments; prompts/get renders one into a list of messages the client can send. Nothing about the mechanism is surprising. What is surprising is how much of a team's operational knowledge fits into one, which is chapter 6.

Transports#

stdio. The client spawns your server as a subprocess and speaks newline-delimited JSON over its standard input and output. Chapter 3 uses it. Anything your server writes to stdout that is not a protocol message corrupts the stream — this is the single most common way a first server fails, and it is usually a stray print().

Streamable HTTP. One endpoint, POST for everything. A response is either JSON or an SSE stream when the server wants to report progress before finishing. The old HTTP+SSE transport with its separate GET endpoint is deprecated.

Two things left this transport in the current revision and both matter. The GET endpoint and resources/subscribe are replaced by subscriptions/listen, a single long-lived POST-response stream you opt into by notification type. And stream resumability is gone: there is no Last-Event-ID, no redelivery, and a broken response stream loses the in-flight request. The client must reissue it as a new request with a new id. Chapter 13 is about designing tools that survive being called twice.

What to take from this#

The protocol is small. Six methods carry almost all real traffic: tools/list, tools/call, resources/list, resources/read, prompts/list, prompts/get. The difficulty in the rest of this book is not protocol complexity — it is that everything you put through those six methods is text in someone's context window, and that the protocol now guarantees you nothing between one call and the next.

Run the capture script. Read the responses. It takes ten minutes and it will make every later chapter concrete.
