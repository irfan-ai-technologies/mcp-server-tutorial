Part 1 — Zero: a server that works · Chapter 3

First server

ledger v0 over stdio, the Inspector, and the shortest useful feedback loop.

Status draftProtocol 2026-07-28Code git checkout ch03-first-server

The smallest useful MCP server is twelve lines. Here is all of it:

Run it with uv run code/labs/hello/server.py and it speaks MCP over stdio. A client will spawn it exactly that way.

The rest of this book is about what happens to those twelve lines when a second client shows up, when the result is large, when two calls need to know about each other, and when you have forty tools instead of one. But it is worth being clear that the starting point really is this small.

What FastMCP did without being asked#

The decorator turned a Python function into a tool definition. The parameter names and type hints became a JSON Schema. The first line of the docstring became the description. None of that is magic — chapter 2 showed you the JSON it produces — but it is worth knowing which parts of your source code are load-bearing:

In your codeOn the wireRead by
Function namenameThe model, when choosing
First docstring linedescriptionThe model, when choosing
Args: entriesPer-parameter descriptionThe model, when filling in
Type hintsinputSchemaThe client, when validating
Return annotationoutputSchemaThe client, when parsing
Everything elseNothingNobody

That last row is the one to internalise. Your comments, your variable names, your careful internal abstractions — none of it reaches the model. If a fact matters for using the tool correctly, it has to be in the name, the description, the parameter descriptions or the schema. There is nowhere else.

The stdout trap

On stdio, your server's standard output is the protocol stream. A stray print(), a library that logs to stdout, a progress bar — any of them corrupt the stream and the client sees a parse error rather than your message. Log to stderr, or better, use the logging module and leave stdout alone. This is the single most common way a first MCP server fails.

From twelve lines to something real#

ledger is the server this book builds. It sits over a synthetic media rights catalogue — titles, licensees, licences with territories and windows, and a corpus of nested agreements. Generate it once:

$ uv run data/generate.py
data/generated/ledger.db  (full, 7.1 MB)
  titles              1,200
  licensees              64
  agreements            470
  licences           13,342
  royalty_lines      60,235
  widest title   T-1152 with 180 licences

That last line is not decoration. One title carrying 180 licences is what turns a correct tool into a context-window failure, and chapter 8 measures exactly what it costs. The dataset is generated deterministically from a seed, so your copy has the same numbers as the ones printed in this book.

The instance, and the instructions nobody writes#

Most servers pass a name and stop. The instructions block is worth more than any individual tool description, because it is the one place you can establish vocabulary. A model that does not know what "window" means in a licensing context will guess, and it will guess something reasonable and wrong.

Write it for someone competent who has never seen your domain. Define the nouns, state the relationships, and say where to start. Three sentences of vocabulary will save you a dozen careful tool descriptions.

Layout#

ledger splits by primitive: app.py holds the instance, tools.py, resources.py and prompts.py register against it, and server.py imports all three so there is exactly one place where the surface is known to be complete.

That import-for-side-effects is worth naming rather than hiding. The modules do not export anything; importing them is what registers their contents. It avoids a circular import between the instance and the things that attach to it, and it means forgetting an import silently removes a tool — so server.py is the file to be careful with, and chapter 7 puts a test on exactly that.

A tool with a real query behind it#

Three things here are deliberate and will come back later.

The description says where to start. "Use this first — every other tool takes a title_id" is orientation, not decoration. A model reading four tool descriptions has to work out the order of operations from them alone.

The limit is clamped, not trusted. A model that asks for ten thousand rows gets a hundred. This is the cheapest possible version of the discipline that chapter 10 turns into a real policy, and it costs one line.

The error is written to be acted on. "query is empty; pass one or more words from the title name" tells the model what to do next. An exception traceback tells it that something went wrong, which it already knew.

Running it#

Over stdio, which is what a local client speaks:

$ cd code/ledger && uv run ledger

Over HTTP, which is chapter 11's subject and available here as a flag:

$ uv run ledger --transport http --port 8000

There is one wrinkle behind that flag that is worth knowing now, because it is invisible until you send a request:

FastMCP 4.0.3 defaults its HTTP app to the pre-2026-07-28 session handshake, and answers a plain request with "Missing session ID". Passing the opt-out through mcp.run() does not reach the app; passing it to http_app() does. That is the kind of thing you find by sending a request, which is why chapter 2 sent one.

Looking at it#

The MCP Inspector is the fastest way to see your server as a client does — it lists tools, resources and prompts, lets you call them with arbitrary arguments, and shows the raw messages. Use it while you are shaping a tool surface. Use it for anything that would otherwise become a print() in a stdio server.

For anything you intend to keep true, use a test instead. Chapter 7.

Checkpoint#

You have a server, it runs on both transports, and you know which parts of your source code are visible to a model. The next three chapters take the primitives one at a time, and then chapter 7 makes the whole thing testable — because from Part 2 onwards, every claim this book makes about ledger is one a test can check.
