Part 3 — Scale · Chapter 13

Failure

Timeouts, cancellation, backpressure, concurrency limits, and retry design now that streams are not resumable.

Status draftProtocol 2026-07-28Code git checkout ch13-failure

Chapter 11 removed a safety net you may not have noticed was there. Under the old transport a broken stream could be resumed: the client sent Last-Event-ID, the server replayed what was missed, and the request carried on.

Specification 2026-07-28

SSE stream resumability and message redelivery are removed. A broken response stream loses the in-flight request, and clients MUST re-issue it as a new request with a new request id.

Read that from the server's side. Your tool was running when the connection dropped. It was not cancelled — it is still executing. The client, which cannot learn its outcome, is now obliged to send it again. You are about to run the same operation twice, concurrently, with no way to tell that is what is happening.

For every tool in this book so far that was free, because they are all reads. This chapter is where ledger gains one that writes.

Idempotency is a promise, not a hint#

Chapter 9 said annotations are promises about your system rather than descriptions of your function. Here is the invoice.

reserve_window holds a licensing window so it cannot be sold twice. Retried naively it reserves the window twice — and the second reservation is indistinguishable from a genuine second request, because on the wire it is one.

The standard answer is a key supplied by the caller. The server remembers the outcome against it, and a repeat returns the stored result instead of running again:

Two decisions in there are the whole chapter.

The insert is the lock. Concurrent retries race to write the row; the primary key lets exactly one win, and the loser reads back what the winner stored. There is no application-level lock to acquire and — more importantly — nothing to release if the process dies holding it. A lock that outlives the process that took it is a worse problem than the one it solved.

The arguments are fingerprinted. Reusing a key with different arguments is refused, loudly. That is what separates an idempotency mechanism from a cache: a cache would cheerfully return the old result, and the second request — a different one, which the client believes has happened — silently never happens at all. That surfaces weeks later as a window nobody reserved.

Where the key comes from#

The caller generates it, which means the model generates it, which sounds alarming until you look at what it has to be: unique per request, stable across retries of that request. A UUID satisfies both, and the parameter description says so in one line.

Do not derive the key from the arguments on the server. That makes two genuinely separate requests with identical arguments collide — reserving the same window twice on purpose is a real thing to want — and it removes the client's ability to say "this is a new request" at all.

Keys need a retention window rather than eternal storage: long enough to cover any retry a client could plausibly make, which is minutes, not months. A table of idempotency keys with no eviction is a disk-space incident with a professional-sounding name.

Timeouts, and who owns them#

Three timeouts exist on every call, usually set by three people who have never spoken.

TimeoutSet byWhat happens when it fires
Client call timeoutThe MCP clientClient gives up; your tool keeps running
Proxy or load balancer idleInfrastructureStream cut; your tool keeps running
Tool timeoutYouYour tool stops

Only the last one stops work. FastMCP takes a timeout per tool, and setting one is how a pathological query stops occupying a worker until the process restarts. Set it below the infrastructure timeout, or you will spend capacity producing results nobody is still waiting for — the most expensive kind of work there is.

When you do time out, say what to do differently. "Timed out after 30s; narrow by territory, or use open_licence_scan for a full walk" is recoverable. "Request timed out" invites the identical request again, and this time the cost is your fault.

Cancellation, and the work that does not stop#

A client that disconnects has not cancelled anything. Python will not interrupt a blocking database call because nobody is listening any more, and FastMCP runs synchronous tool bodies in a thread precisely so they do not block the event loop — which also means they do not notice the loop has given up on them.

Abandoned work still holds your connection pool, your CPU and your database. For anything long, this is the argument for not doing it in a tool call at all: the tasks extension in chapter 15 exists so slow work can outlive the request that started it deliberately, rather than by accident.

Backpressure#

On stdio there was one caller and one call at a time. Over HTTP the question "how many of these run at once" has an answer whether or not you chose it — and it is usually your database connection pool.

The failure that produces is the bad kind. Everything slows down together, health checks start timing out, and the fleet drops out of rotation simultaneously, which is exactly the scenario chapter 11's health endpoint was written not to participate in.

Pick the limit deliberately and reject past it rather than queueing indefinitely. A fast "busy, retry shortly" leaves the caller able to act. A request that queues for ninety seconds and then fails has spent the caller's patience and your capacity and taught nobody anything.

The one to get right

Retry storms compound. A client that retries on timeout, behind a proxy that retries on 5xx, in front of a pool that is already saturated, turns a blip into an outage. If you add retries anywhere, add jitter and a ceiling, and make sure at most one layer is retrying.

What to design for#

Assume every call may run twice, concurrently, and that the caller may see the result of neither. That sounds pessimistic. It is just what "no resumability" means, read carefully.

Reads are fine. Writes need a key, and the key needs enforcing rather than announcing. Long work needs somewhere to live that is not a request, which is chapter 15. And every limit in your system has a number: if you did not choose it, your database chose it, and it chose badly.

Chapter 14 is the opposite problem — not what happens when a call fails, but what it costs when a hundred identical ones succeed.
