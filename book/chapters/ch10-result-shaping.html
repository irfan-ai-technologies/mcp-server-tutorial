Part 2 — The client's point of view · Chapter 10

Result shaping

Content versus structured output, pagination, truncation, and the failure mode where one successful call ends the conversation.

Status draftProtocol 2026-07-28Code git checkout ch10-result-shaping

Chapter 8 put a number on the problem: one correct call to find_licences cost 15,118 tokens, nearly eleven times the entire tool surface it came from. This chapter fixes it, and the fix is worth about forty lines.

The result is not just cheaper. It tells the model more than the dump did.

The dump was never the answer#

Start with what the user actually asked. "What have we sold on The Winter Cartograph?" is a question about coverage — which markets, which rights, what is still running. One hundred and eighty rows of licence records contain that answer the way a filing cabinet contains a summary.

The naive tool returned every row because that was the only thing it knew how to do. It had no total, no notion of "too many", and no way to say you asked for more than you want. So it answered the literal question and left the model to do the aggregation, in context, at fifteen thousand tokens.

Three things every list-returning tool needs#

A total. One cheap COUNT(*), and suddenly the model knows whether it is looking at everything or at a fragment. This is the single highest-value field you can add to a result and almost nobody returns it.

A default limit. Not a maximum — a default. An optional limit with no default gets omitted; a limit that defaults to 20 means the expensive path has to be chosen deliberately.

The shape of what was left out. This is the part people skip, and it is what turns a truncated result from a frustration into a next step.

The two histograms are the whole idea. A hundred and sixty rows were withheld; {"CA": 11, "KR": 10, "DE": 9, ...} and {"active": 63, "expired": 117} describe them in about three hundred characters. A model that wanted German coverage now knows there are nine rows and can ask for exactly those. A model that wanted current deals knows that two thirds of what it asked for has expired.

Note also what happens when nothing was truncated: none of it appears. A complete result is total, returned and the rows. Do not make people pay for advice they do not need — there is a test for that.

The measurement#

Against chapter 8's numbers:

CallNaivePaged
find_licences, no filter15,118 tokens1,930 tokens7.8× smaller
find_licences, active only5,312 tokens1,898 tokens2.8× smaller
find_licences, one territory253 tokens267 tokens5.5% larger
Fixed tool surface1,400 tokens1,474 tokens5.3% larger

Both increases are real and both are worth naming. The narrow call grew by fourteen tokens because it now carries total and returned. The surface grew by seventy-four because the tool gained a parameter and a description that warns about breadth.

You pay a fixed 5.3% and a rounding error on cheap calls, to remove thirteen thousand tokens from the expensive one. That is the trade, stated honestly, and it is not close.

The budget test did its job#

Chapter 9 put a ceiling on any single tool definition at 1,200 characters. Making this change pushed find_licences to 1,226 and the suite went red.

FAILED tests/test_budget.py::test_no_single_tool_dominates
AssertionError: find_licences is 1,226 characters — usually a schema that
grew a nested object or a long enum

That is the test working, not the test being annoying. The budget was raised to 1,400 in the same commit, with the reason written beside it in the source. Six months from now the question "why is this 1,400?" has an answer, and the next person to push against it has to write one too.

Cursors, and when you need them#

What is described above is a limit, not pagination. There is no cursor and no way to ask for rows 21 to 40.

That is deliberate. A model that has been told 180 matched, here are 20, here is where the rest are should almost always narrow rather than page. Paging through 180 licences twenty at a time is nine round trips and the same ten thousand tokens, arriving more slowly.

Add a cursor when the caller genuinely needs completeness — an export, a reconciliation, a job that has to touch every row. Then it is a real requirement rather than a fallback for a query that should have been narrowed. When you do add one, make it opaque: an encoded position, not an offset, so the meaning of "page 3" cannot drift under a concurrent write. And note that a cursor is state, which after 2026-07-28 is state you mint and hand back as an argument. Chapter 12 is entirely about doing that well.

Truncating text, not rows#

Everything above is about lists. The other common oversized result is one large document — a contract, a log, a report — and the instinct is to cut it at N characters and append an ellipsis.

Do better, cheaply. Say how much was cut and in what units. Cut on a structural boundary so the fragment is still parseable. And return an address for the rest — a resource URI, an identifier, something the model can follow — so truncation is a door rather than a wall. Chapter 21 builds the general version of that for a whole corpus.

Never truncate silently

A result that has been cut without saying so is worse than an error. The model will reason confidently over a fragment it believes is complete, and the user will get a specific, plausible, wrong answer. If you take something out, say so in the payload.

Errors are results too#

The same discipline applies to failure. "Too many results" wastes the call; "4,182 licences match; narrow by territory or status" costs a dozen tokens and ends the loop. A refusal that names the number and the lever is a cheap result, not a failed one.

What Part 2 established#

Your server is a prompt, and it has a bill. The fixed part is your tool surface — about 1,470 tokens for ledger, measurable, budgeted and enforced in CI. The variable part is what your tools return, and it dominates: one careless call outweighs every description you might have trimmed.

Three habits carry into the rest of the book. Measure before optimising. Return totals and the shape of what was withheld, not just rows. And when something is too big, say so in a way that names the next move.

Part 3 changes the question from what a call costs to what happens when there are many of them, from many clients, against a server that the protocol no longer allows to remember anything.
