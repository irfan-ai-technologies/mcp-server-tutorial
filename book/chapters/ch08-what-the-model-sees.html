Part 2 — The client's point of view · Chapter 8

What the model actually sees

Token-accounting your own tool surface, measured on ledger rather than borrowed from a blog post.

Status draftProtocol 2026-07-28Code git checkout ch08-token-audit

Up to here the book has been about what your server does. From here it is about what your server costs, and the unit is not milliseconds or dollars — it is space in a context window you cannot see, do not pay for, and share with everything else the user is doing.

The uncomfortable part is that you can measure all of it, and almost nobody does.

What your server costs before anyone asks it anything#

A client connecting to ledger loads the tool definitions, the resource and template metadata, the prompt list and the instructions block. That happens whether or not a single tool is called. Here is the bill, produced by code/labs/token-audit/audit.py against the code in this repository:

About 1,400 tokens for four tools, two templates, one resource and two prompts. On a 200k window that is under one percent, and you might reasonably conclude there is nothing to see here.

There is, and it is arithmetic. find_licences alone is 267 tokens — a tool with three parameters and a one-line description. Scale that honestly: a server generated from a REST API with forty endpoints lands somewhere between eight and eighteen thousand tokens. Connect four such servers, as any real workspace does, and the user is starting every conversation forty to seventy thousand tokens down before typing a word.

That is the number the ecosystem has been rediscovering for a year, and it is not caused by any single badly-written server. It is caused by every server being individually reasonable.

Two things worth checking on your own server

What does tools/list cost in total? And what is the largest single tool definition? A schema with deeply nested objects or a long enum can quietly be worth several hundred tokens on its own.

Characters are exact; tokens are a claim#

Every table in this chapter has two columns for a reason. Character counts are verifiable — you can count them yourself and get the same answer. Token counts depend on the tokenizer, and Claude, GPT and Llama do not agree.

The committed report was generated with an estimator at 3.6 characters per token, because the machine that produced it could not reach a tokenizer's encoding file. Install tiktoken and re-run and you will get exact o200k_base counts, and the report will say so in its header. The estimate is close enough that none of the conclusions move, and the honest framing matters more than the precision: a token count quoted without naming a tokenizer is folklore.

What survives the disagreement is the shape of the answer. That is what the rest of this chapter is about.

The number that should worry you#

One tool call — a correct one, against a valid title, returning accurate data — costs 15,118 tokens.

That is nearly eleven times the entire tool surface it came from. Every efficiency you might win by trimming descriptions, dropping a tool, or tightening the instructions block is erased many times over by a single unfiltered call.

And the same call, narrowed to one territory, costs 253 tokens. The information the user actually wanted was in there for a quarter of a thousand tokens. The other fourteen thousand eight hundred and sixty-five were the cost of not asking a better question — a factor of sixty, for one omitted argument.

Why this is the server's fault#

The natural response is that the model should have narrowed the query. Sometimes it should. But look at what find_licences tells a model about the consequences of not narrowing:

Nothing. The description says "Licences attached to a title." The schema says territory is optional. There is no indication that omitting it might return one row or one hundred and eighty, no total returned alongside the rows, and no error when the result is absurd. The model has no way to know the difference between a cheap call and an expensive one until after it has paid.

A tool that can return 180 rows and does not say so is a tool designed to be misused. Chapter 10 fixes exactly this, and the fix is smaller than you would expect.

The failure mode this produces#

The obvious harm is cost, and it is the least interesting one. Three others matter more.

The conversation ends. A user with a 200k window and three servers connected has perhaps 130k of working room. Two unfiltered calls and a long document and they are compacting mid-task, losing the earlier reasoning. From their side the agent "forgot" what it was doing. It did not forget; you filled the window.

Quality degrades before it fails. Attention over ten thousand tokens of near-identical JSON rows is not free. A model asked to find the two exclusive licences in that list will do worse than one handed six relevant rows, and it will do worse silently — with a fluent, confident, wrong answer rather than an error.

The cache breaks. A large result inserted mid-conversation invalidates everything cached after it. Chapter 14 puts numbers on that; for now, note that a 15,000-token result is not a one-off charge but a change to the shape of every subsequent turn.

Measure your own#

The audit script is about a hundred lines and most of it is formatting. The parts that matter:

Point it at your own server, replace the list of representative calls with the ones your users actually make, and commit the report. Two habits follow from having it:

Run it in CI and fail the build when the surface grows past a budget you chose deliberately. A tool surface creeps the way a Docker image creeps — one reasonable addition at a time — and the only defence is a number someone has to argue with.

Run it against the largest plausible result for every tool, not a typical one. Typical results tell you nothing; a server is judged by its worst call, because a model will find it.

What the rest of Part 2 does with this#

Chapter 9 is about the 1,400 tokens: making every one of them earn its place, since description text is the only thing standing between a model and a wrong tool.

Chapter 10 is about the 15,118: what a tool should return, what it should refuse to return, and how to tell a model that a query is too broad before it pays for the answer.

Then Part 3 scales it, and Part 4 attacks the surface itself — because a server with forty tools cannot be fixed by writing better descriptions for all forty.
