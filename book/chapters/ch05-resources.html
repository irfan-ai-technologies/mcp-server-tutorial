Part 1 — Zero: a server that works · Chapter 5

Resources and templates

When a resource beats a tool, and why most servers get this backwards.

Status draftProtocol 2026-07-28Code git checkout ch05-resources

Most MCP servers have no resources. Their authors read the specification, noticed that resources are reads and tools can also read, and concluded that resources were a redundant primitive. That conclusion is wrong, and the cost of it shows up in Part 4 as a context problem that did not need to exist.

The distinction is who decides#

A tool is model-invoked: the model reads descriptions and chooses to call it. A resource is application-invoked: the client decides to load it and addresses it by URI.

So the question is never "is this a read?". It is: does the client already know it wants this?

SituationPrimitiveWhy
User has a title open in the UIResourceThe client knows which one; no reason to make the model ask
"Which titles are about lighthouses?"ToolOnly the model can choose the arguments
The catalogue's vocabulary and sizeResourceUseful before any question is asked
"What did we license to Northwind in Q3?"ToolThe parameters come from the conversation
One node of a document hierarchyResourceAddressable, so it can be walked

Notice that the same underlying data can legitimately appear in both. That is not duplication, it is two access paths for two different deciders.

An overview worth loading first#

This is the most under-used shape in MCP: a small, stable document that teaches the shape of the data before anyone asks a question. It tells a model that territories are two-letter codes and which ones exist, that rights is a closed vocabulary and what is in it, that royalties are reported by quarter and which quarters exist.

Without it, a model asked about "streaming rights in Britain" has to discover by trial that the values are svod and GB. With it, the first call is right.

Now notice what the overview does not contain: any actual title. There are 1,200 of them. An overview that grows with the catalogue is not an overview, it is a dump with a friendly name, and a test in this repository enforces the difference:

assert "titles" not in payload["vocabulary"]
assert len(json.dumps(payload)) < 4_000

Pick a size budget for anything a client might auto-load, write it as an assertion, and let it fail when someone adds a helpful list of everything.

Templates: one resource, many addresses#

ledger://title/{title_id} is a resource template. It appears in resources/templates/list as a pattern rather than a concrete URI, and a client substitutes the identifier.

The obvious objection: get_title already exists and returns nearly the same data. Why both?

Because the deciders differ. A UI where the user has clicked on a title can attach ledger://title/T-1152 to the conversation before the model does anything. The tool is for the case where the model has to work out which title is meant. Removing the resource does not save you anything — the data still gets loaded — it just forces a round trip and a decision through the model.

Design your URI scheme as if people will bookmark it, because effectively they will. ledger://title/{id} and ledger://agreement/{id} are stable addresses for stable entities. Avoid encoding queries into URIs: the moment a URI has a filter in it, you have built a tool with an awkward calling convention.

Links, not subtrees#

The agreement resource is where this chapter starts pointing at Part 4. Agreements nest: amendments hang off masters, side letters off amendments, and the terms that apply are the ones nearest the leaf. There are 470 of them, some chains three deep.

The tempting implementation returns the whole subtree from the root. It is less code and it works beautifully in a test with four agreements. At real depth it returns a document nobody can read and everybody pays for.

What ledger://agreement/{id} returns instead is one node, its parent as a URI, and its children as URIs with just enough metadata — kind, reference, signing date — to choose between them. A reader walks. Each step is small, each step is a decision, and nothing is loaded that was not chosen.

A test pins the shape:

for child in payload["children"]:
    assert child["uri"].startswith("ledger://agreement/")
    assert "children" not in child, "a child must be a link, not a subtree"

This is progressive disclosure in its simplest form, and it is available to you in chapter 5 rather than chapter 21 because it needs nothing but a URI scheme and some restraint. Chapter 21 generalises it: table-of-contents resources, drill-down over a corpus, and how to shape a hierarchy that was not designed to be walked.

Mime types and what the client does with them#

Declare mime_type honestly. A client that knows it has JSON can parse and render it; one that is told text/plain will show a wall of braces. If a resource returns Markdown, say so — some clients render it, and a rendered document is far more usable to a human sitting next to the model.

Resources can also return binary content as blobs. Images and PDFs work; they also cost far more context than people expect, and chapter 8 will make you aware of it.

Change notification, as it now works#

Specification 2026-07-28

resources/subscribe and resources/unsubscribe are gone, along with the HTTP GET endpoint. In their place is subscriptions/listen: a single long-lived POST-response stream that a client opts into by notification type (toolsListChanged, promptsListChanged, resourcesListChanged, resourceSubscriptions). The server acknowledges and tags each notification with io.modelcontextprotocol/subscriptionId.

List results also now carry ttlMs and cacheScope, which let a client cache instead of polling. Between the two, most servers should be quieter than they were. ledger's catalogue does not change during a conversation, so it uses neither — and, as chapter 2 established, FastMCP 4.0.3 does not emit the cache fields yet regardless. Chapter 14 is where caching becomes something you decide rather than something your library does or does not do.

Checkpoint#

Resources are for what the application knows it wants, tools are for what the model has to choose. An overview resource that teaches vocabulary is cheap and unusually valuable. And a hierarchy exposed as linked nodes rather than nested documents is the whole of progressive disclosure, sixteen chapters early.
