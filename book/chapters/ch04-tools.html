Part 1 — Zero: a server that works · Chapter 4

Tools

Signatures, JSON Schema 2020-12, structured content, annotations, and errors written for a model rather than a human.

Status draftProtocol 2026-07-28Code git checkout ch04-tools

A tool definition is a prompt fragment with a function attached. Everything in this chapter follows from taking that literally.

The model does not run your tool and observe the result the way a developer does. It reads a name, a sentence, a few parameter descriptions and a schema, decides whether this is the right tool for what the user asked, guesses at arguments, and finds out whether it guessed right by being wrong. Your job is to make the guess easy.

The name is the first sentence#

Tool names are read together, as a set, before any description is considered carefully. search_titles, get_title, find_licences, licence_detail — that set tells you the shape of the domain before you read a word of prose.

Two failure modes are common. The first is names that overlap: get_licence and fetch_licence_info in the same server will be chosen between at random, and no amount of description fixes it. The second is names that describe your implementation rather than the user's intent — query_licence_view_v2 is honest about your database and useless to a model.

Verb-first, domain nouns, and distinct at a glance. If two tools need a paragraph to tell apart, they should probably be one tool with a parameter.

The first line of the docstring is the whole description#

FastMCP takes the first line as the tool description and lifts Args: entries into per-parameter descriptions. Everything below the first line and outside Args: is invisible.

Write the first line as an answer to when should I use this?, not what does this do? "Licences attached to a title" is adequate. "Licences attached to a title — use after search_titles, and narrow by territory when you only need one market" is better, and costs eight tokens.

Let the schema do the validating#

The status parameter above is a Literal, and that one change does three things a runtime check cannot.

The allowed values appear in the schema, so the model knows them before calling rather than discovering them by failing. The client can reject a bad value without a round trip. And the tool body loses a branch — there is no longer any code in find_licences that handles a status it does not recognise, because one cannot arrive.

The general rule: anything that can be expressed as a type should be. Enumerations, optionality, integer bounds, string formats, required-versus-optional. The revision loosened this deliberately.

Specification 2026-07-28

inputSchema and outputSchema now allow any JSON Schema 2020-12 keywords, and structuredContent allows any JSON value, with defined $ref resolution and bounds on composition keywords. You are no longer confined to a subset.

Being able to express a constraint is not the same as it being worth expressing. A schema so precise that the model cannot construct a valid call is worse than a loose one — chapter 9 is about that trade-off. Start with types you already have and tighten where the model actually gets it wrong.

What comes back#

A result carries content — blocks of text, images or embedded resources — and structuredContent, the same data as JSON. Return a typed value from a Python function and FastMCP produces both, plus an outputSchema.

There is a wrinkle. JSON Schema wants an object at the top level, so a tool returning a list gets wrapped:

"outputSchema": {
  "properties": {"result": {"items": {...}, "type": "array"}},
  "required": ["result"],
  "x-fastmcp-wrap-result": true
}

Your list[dict] is {"result": [...]} on the wire. Worth knowing before you write a client, and worth knowing before you assume the shape a model sees is the shape you returned.

The deeper question — how much should come back at all — is chapter 10's, and find_licences is deliberately wrong about it until then. It returns every row it finds, with no total and no limit. For the title with 180 licences, that is every one of them.

Errors are messages to a model#

Chapter 2 showed that a failed tool is a successful JSON-RPC response carrying isError: true. The distinction is not pedantry: it means the failure text goes to the model, in the conversation, as something to act on.

So write it that way.

KeyError: 'T-nope'no title 'T-nope'; use search_titles to find oneNames the recovery

The test is whether a competent colleague who cannot see your code could act on the message. If they would have to ask a follow-up question, the model will guess instead.

Reserve exceptions that are not ToolError for things the model genuinely cannot fix — a database that is down, a bug in your code. Those should be protocol-level failures and should page you, not be politely explained to a language model.

Annotations#

Every tool in ledger carries the same three hints:

READ_ONLY = {"readOnlyHint": True, "destructiveHint": False, "idempotentHint": True}

These are how a client decides what it may run without asking a human. A read-only, idempotent, non-destructive tool can be retried, run in parallel, and called without a confirmation dialog. A tool that lacks the hints gets treated conservatively, which usually means a prompt in front of the user every single time.

They are hints, not enforcement — nothing stops a lying server. Treat them as a contract you keep, and note that "idempotent" is a promise about your system, not your function. Chapter 13 comes back to this when retries stop being hypothetical.

What should not be a tool#

Three things get made into tools that should not be.

A thing the client already knows. If the application can put it in context without asking, it is a resource. Chapter 5.

A procedure the user invokes deliberately. "Run the quarterly clearance review" is a prompt, not a tool. Chapter 6.

Every endpoint you happen to have. The most expensive mistake in MCP is generating one tool per REST route. Forty tools nobody uses is forty tools every conversation pays for, and a model that has to read all of them to choose one. Parts 2 and 4 are largely about digging out of this, and not doing it is much cheaper.

Checkpoint#

ledger has four tools, each with a description written for a model, a schema that rejects bad input before the body runs, errors that name a recovery, and annotations that tell a client what it is safe to do. It is also still returning 180 rows when asked nicely, which is the subject of chapter 10.
