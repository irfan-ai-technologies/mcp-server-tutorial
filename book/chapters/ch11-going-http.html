Part 3 — Scale · Chapter 11

Going HTTP

Streamable HTTP, running stateless behind a load balancer, and what horizontal scale actually costs you.

Status draftProtocol 2026-07-28Code git checkout ch11-http

stdio is a fine transport and most servers should stay on it. The client spawns your process, it lives and dies with the conversation, and there is exactly one of it. Almost nothing in Part 3 applies.

Going to HTTP is not a deployment detail. It is the decision to have many of something — many clients, many instances, many concurrent calls — and every chapter in this part is a consequence of it.

What the revision handed you#

Before 2026-07-28, an HTTP MCP server was stateful by construction. A client called initialize, got back an Mcp-Session-Id, and every subsequent request carried it. That session was real state on one instance, which meant sticky routing, session affinity at the load balancer, and a rolling deploy that dropped every conversation in flight.

Specification 2026-07-28

Protocol-level sessions and the Mcp-Session-Id header are removed from the Streamable HTTP transport. List endpoints no longer vary per connection. The initialize/notifications/initialized handshake is gone; every request carries its protocol version and client capabilities in _meta.

So a request is now self-contained. Any instance can serve it, you can scale on CPU like any other service, and a deploy is a deploy rather than an outage. That is a large gift and it comes with one bill, which chapter 12 pays: anything you used to keep in a session, you now have to hand to the client and take back.

Turning it on, and checking that you did#

Chapter 3 flagged this and it is worth repeating here because it is the single most likely way to deploy a server that is not doing what you think:

FastMCP 4.0.3 defaults stateless_http to False, which keeps the old handshake alive for older clients. Passing the flag through mcp.run() does not reach the app. A server started that way answers a plain request with {"error": {"code": -32600, "message": "Bad Request: Missing session ID"}}, and you will not see it unless you send one.

An app, not a flag#

Once you are serving HTTP, you need the things any HTTP service needs, and MCP gives you none of them. ledger builds its own ASGI app and mounts the MCP one inside it.

Health. Two different questions get one endpoint here, and the docstring says why that is only acceptable because the sole dependency is a local file:

Liveness asks whether the process is wedged. Readiness asks whether it can serve. Wire a readiness probe to a database round trip and a two-second blip in that database takes your entire fleet out of rotation simultaneously — every instance fails the same check at the same moment, and nothing is left to serve the traffic that was fine.

A request id. Without sessions there is no connection to correlate by, so an id per request is the only thread from a log line to the call someone is complaining about:

Honour an inbound x-request-id rather than always minting one. A gateway or the client may already have issued it, and a second id breaks the trace exactly where it crosses a boundary. Chapter 16 takes this further into OpenTelemetry, where the protocol has a defined place to put trace context.

What "stateless" does not mean#

It means no protocol state between requests. It does not mean your server has no state — ledger has a database — and it does not mean your process is free of memory.

The distinction that matters: state which is shared and authoritative (your database) is fine, because every instance sees the same thing. State which is local to one process is now a bug, because the next request will land somewhere else. An in-memory cache keyed by something a client sent you, a dictionary of "open" things, a counter — all of these work perfectly on one instance and fail intermittently on four, which is the worst way to fail.

The test that finds this

Run two instances behind anything that round-robins, and send alternating requests. Any per-process state shows up immediately as a coin flip. This is worth doing before you believe a server is stateless, because the failure mode under one instance is silence.

Concurrency#

On stdio, calls arrive one at a time from one client. Over HTTP they arrive together, from several clients, and your tool bodies are suddenly concurrent code.

FastMCP runs synchronous tool functions in a thread by default, which keeps a blocking database call from stalling the event loop — ledger's tools are ordinary def functions for exactly this reason. That is a sensible default and it has an edge: anything shared between those threads needs to be safe for them. SQLite connections are not, which is why db.connect() opens one per call rather than holding a module-level handle.

Connection-per-call is the right default and it does not scale forever. When it stops being enough you want a pool, and a pool has a size, and that size is a concurrency limit whether or not you chose it deliberately. Chapter 13 is about choosing it.

Streams break, and nothing comes back#

One removal in this revision changes retry design more than its two lines suggest.

Specification 2026-07-28

SSE stream resumability and message redelivery are removed from Streamable HTTP — no Last-Event-ID header, no event ids. A broken response stream loses the in-flight request, and clients MUST re-issue it as a new request with a new request id.

A tool call that was running when the connection dropped has not been cancelled. It is still executing somewhere, and the client — which has no way to learn its outcome — will send it again. Whether that is harmless or a disaster depends entirely on whether your tool meant it when it claimed idempotentHint.

Every ledger tool is a read, so re-execution costs nothing but time. The moment one of them writes, that stops being true, and chapter 13 is where it is dealt with properly.

What to check before you call it deployed#

A short list, each of which is a test rather than a habit:

A plain tools/call with no session header and no prior request succeeds. Health returns without touching anything slow. Two instances behind a balancer produce identical answers to identical requests. The same call issued twice leaves the system in the same state. And a request id appears in every log line your server writes.
