Prompts

The least-used primitive: what it is actually for, and when to skip it.

Status draftProtocol 2026-07-28Code git checkout ch06-prompts

Prompts are the primitive people skip. The reasoning is always the same: anyone can type that themselves. It is true, and it is true right up until five people type it five different ways and two of them get a confidently wrong answer.

A prompt is where a domain's standard question lives, with the method already correct.

User-invoked, and that changes everything#

Tools are chosen by the model. Resources are loaded by the application. Prompts are picked by a person — from a slash-command menu, a palette, a button. The user has already decided what they want; the prompt supplies the wording.

That has one consequence worth stating plainly: a prompt costs nothing until it is used. Clients list prompt names and descriptions, but the body only enters the conversation when someone picks it. Compare that with a tool, which pays rent in every context window whether or not it is called.

So the economics are the reverse of tools. A server with forty tools is in trouble. A server with forty prompts is a well-documented server.

What a good prompt actually contains#

The valuable part is not the question. It is step 2 arriving before step 3.

A model asked "can we license this in Germany?" will, left alone, look for an available window and report one. That answer is wrong whenever an unexpired exclusive already covers the territory — and it is wrong in the worst way, because it is specific, plausible, and about to be repeated to a counterparty.

Checking exclusivity first is not a modelling insight. It is what someone who has done the job for six years knows and a new joiner does not. That knowledge normally lives in a person, gets partially written into a wiki page nobody opens, and is absent from every conversation with a model. A prompt is somewhere to put it.

Look at the other instructions in there. If several match, list them and stop — do not guess which one is meant. Name the agreement each blocking licence sits under, so the answer can be checked against the paper. If the licence data is ambiguous, say so rather than resolving it. Each of those is a rule for when to stop, and stopping correctly is most of what makes an answer trustworthy.

Prompts do not call tools#

A prompt returns text. It does not execute anything, and it does not answer anything — it assembles a well-formed question and hands it to the model, which then uses the tools it already has.

This is a feature. The prompt stays valid when the tools change, works with whatever model the client is running, and can be read and argued about by the person whose expertise it encodes. That last point matters more than it sounds: a rights manager can read clearance_check and tell you it is missing a step. They cannot read your orchestration code.

Arguments, and the ones you should not add#

clearance_check(title, territory, rights="svod") takes what the user knows: the thing they are asking about. It does not take a title_id, because a person invoking this from a menu has a name in their head, not an identifier — resolving the name is step 1, and step 1 is written to stop if the name is ambiguous.

Two habits are worth keeping. Arguments should be things a human has to hand, not identifiers your system happens to use. And defaults should be the common case, so the prompt is useful with the minimum typed.

Missing arguments are an error, not a gap to be papered over:

$ prompts/get clearance_check {}
ValueError: Missing required arguments: {'territory', 'title'}

Testing text#

ledger's prompt tests assert on generated wording, which normally deserves suspicion. It is defensible here for one reason: the value of a prompt is the procedure it encodes, and a procedure that quietly loses a step is a regression even though nothing raises.

assert text.index("exclusive") < text.index("windows already committed"), (
    "checking availability before exclusivity is how you clear something "
    "that is already sold"
)

Assert on the load-bearing parts — the ordering, the stop conditions, the refusals — and leave the prose alone. A test that breaks when you fix a typo trains people to delete tests.

The other prompt: reviews#

window_review is a different shape. It does not ask a question with an answer; it asks the model to find problems, in a stated order of severity, with counts before examples and identifiers attached so each finding can be checked.

Its last instruction is the interesting one:

If a title carries more licences than you can review carefully, say how many there are and ask which territories matter rather than skimming all of them.

That is the first appearance in this book of a theme that runs through Part 4. The catalogue contains a title with 180 licences. No amount of prompt engineering makes 180 licences reviewable in one pass; the honest move is to say so and narrow. Encoding "notice when there is too much and stop" into the prompt is the cheapest available mitigation, and it works today. Chapters 19 through 23 are about the expensive ones that work better.

When to skip prompts#

If your server exposes one tool and there is one obvious thing to do with it, a prompt adds a menu item and no knowledge. Prompts earn their place when there is a method — an order of operations, a set of stop conditions, a house convention for how an answer should be presented. If you cannot name the expertise you are encoding, you are writing a shortcut, not a prompt.

Checkpoint#

Prompts are free until used, so the constraint on them is your own clarity rather than anyone's context budget. Put the order of operations in them, put the stopping rules in them, and let the person whose job it is read them.
