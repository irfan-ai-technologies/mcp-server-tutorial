Part 3 — Scale · Chapter 12

Life after sessions

Server-minted handles: shape, TTL, storage, revocation, idempotency keys — and how to stop a handle becoming a session by another name.

Status draftProtocol 2026-07-28Code git checkout ch12-state-handles

Here is the bill for chapter 11. The protocol used to give you a session — somewhere to put the fact that this client, in this conversation, was halfway through something. It does not any more, and nothing was put in its place except a technique.

Specification 2026-07-28

Protocol-level sessions are removed. "Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments."

One sentence in a changelog, and an architectural decision underneath it.

Two kinds of handle#

The word "handle" covers two designs that behave completely differently, and picking the wrong one is how a stateless server quietly becomes a stateful one.

Signed, self-containedStored
What the token isThe state itself, signedA key into a shared store
Server storageNoneA row, with a TTL
Works on any instanceImmediatelyOnce the store is shared and consistent
Size limitWhat fits in an argumentUnbounded
Snapshot isolationNo — describes a queryYes — materialised
RevocationOnly by expiry or key rotationDelete the row
What it costs youDiscipline about sizeA store, eviction, and a way for instances to disagree

Most servers reach for the stored version because it is the one that resembles a session, and most of them needed the signed one. If the state is small and describes what the caller asked for rather than what the answer was, signing it is strictly better: there is nothing to evict, nothing to replicate, and no instance that can disagree with another.

Signing one#

ledger's handle is kind.payload.signature — a URL-safe base64 JSON body with an expiry, and an HMAC over it:

Three decisions in there are worth defending.

The body is readable. A client can decode a handle and see what is in it. That is fine — nothing secret goes inside — and it is better than the alternative, because a handle you can read is a handle you can debug. What the client cannot do is change one.

The expiry is inside the signature. So it cannot be extended by the holder, and no server has to remember when anything was issued. Expiry becomes arithmetic rather than bookkeeping.

The kind is checked. A scan handle must not be accepted where an export handle is expected, even though both verify against the same key. Kind confusion is how one feature's token silently becomes another feature's authorisation, and the check costs one comparison.

The key is not a per-process secret#

A random key generated at startup feels more secure and is worse in every way that matters here. Every deploy would invalidate every outstanding handle, and two instances would reject each other's tokens — which is precisely the failure that losing sessions was supposed to remove. It is a shared signing key, like any other shared signing key, and it rotates the way those do: accept the previous one for a window, then stop.

A handle that is a continuation#

Chapter 10 deliberately gave find_licences a limit and no cursor, arguing that a model told "180 matched, here are 20, here is where the rest are" should narrow rather than page. That holds for questions. It does not hold for reconciliation, where missing a row is a defect rather than an inconvenience.

Each page returns the handle for the page after it. The position lives in the token, not on the server, and that single property is what makes the whole thing work: re-reading a handle returns the same page, so a client that retries after a dropped stream sees the rows again rather than skipping them.

Compare that with an offset kept server-side, where a retry advances the cursor and the rows in between are silently lost. The client cannot tell. Nothing errors. You find out at the end of the quarter when the reconciliation is short.

Proving it survives the instance that issued it#

The claim worth testing is not that the handle round-trips. It is that a handle minted by one server is honoured by another that has never heard of it:

Reloading the module is a stand-in for a second process behind a load balancer. It is crude and it catches the real failure, which is someone quietly adding a dictionary to hold "open scans" — that test goes red the moment the handle depends on the instance.

When you genuinely need a stored handle#

Three cases, and they are narrower than they look.

Snapshot isolation. An export that must reflect the catalogue as it was when the export began, not as it drifts underneath. A signed handle describes a query and will happily show you rows inserted since.

State too large to carry. A materialised result of ten thousand identifiers does not belong in a tool argument.

Revocation. If "cancel this" has to take effect immediately rather than at expiry, something has to be deleted, and a signed token has nothing to delete.

When you do need one, the handle is still signed — the token identifies a row rather than carrying state, and the signature stops a client enumerating other people's rows by guessing. And it gets a TTL, an eviction job, and a test that the TTL is actually enforced, because a store of handles with no eviction is a memory leak with a business-friendly name.

Scoping a handle to who asked for it#

ledger is single-tenant so far, which lets this chapter stay about mechanism. It will not stay that way: chapter 17 makes it multi-tenant, and at that point the tenant goes inside the signed body.

This is the one thing to get right the first time. A handle that encodes a position but not an identity is a token that lets whoever holds it read whatever it points at. If the scan belongs to one studio, the handle says so, and the tool checks it against the caller — every time, not just when the scan opens.

Where else this technique lands#

Once you see handles as "the state, signed, in an argument", they turn up everywhere the protocol used to offer a session.

Multi round-trip requests are the clearest case. A server returning resultType: "input_required" has to reconstruct its position when the client retries with answers — and the specification gives it requestState to carry exactly that. Same technique, standardised slot.

The same shape covers a long-running job's ticket, a draft being assembled across calls, and an idempotency key for a write — which is chapter 13.

Checkpoint#

Sessions are gone and the replacement is better, but it is not free: you have to decide what the state is, sign it, expire it, bind it to a purpose, and eventually bind it to a caller. In exchange, any instance serves any request, and a retry after a dropped connection is safe rather than lossy.

Chapter 13 is about the rest of that sentence — what happens when the connection drops, the call times out, or the same request arrives twice.
