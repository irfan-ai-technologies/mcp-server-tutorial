Testing without an LLM

In-process client, golden transcripts, contract tests over the tool surface. Everything after this depends on it.

Status draftProtocol 2026-07-28Code git checkout ch07-testing

There is a habit in this field of testing servers by talking to them. You wire up a model, ask it something, read the answer, and decide it looks right. It is slow, it costs money, it is non-deterministic, and when it fails you cannot tell whether the server, the prompt or the model was wrong.

Almost everything worth knowing about an MCP server can be checked without a model in the loop, in under two seconds. That is what this chapter builds, and every claim the rest of this book makes about ledger rests on it.

Talk to it as a client, in-process#

The key move is to test through a real MCP client rather than by calling your Python functions. Calling find_licences() directly tests your SQL. Calling it through a client tests the schema, the serialisation, the error path, the annotations and the registration — all the parts that only exist once the function has become a tool.

Two things are doing real work here. The client is constructed against the server object directly, so there is no subprocess and no socket — the whole round trip happens in memory, which is why the suite finishes in under two seconds. And the catalogue is regenerated into a temporary directory for every run, with LEDGER_DB pointed at it, so a test run never depends on or disturbs whatever the reader has in data/generated/.

Deterministic fixtures matter more here than in ordinary testing. Several assertions later in this book are about sizes — how many rows, how many tokens — and a fixture that varies makes those assertions meaningless.

Contract tests: the surface itself#

Before testing what tools do, test what tools exist.

This looks trivial and catches a specific, real failure. ledger registers its primitives by importing modules for their side effects; a missing import in server.py silently removes a tool. Nothing raises. The server starts, works, and quietly no longer does one of the things it advertises.

The same test also makes tool removal a deliberate act. Once your server has users, the tool surface is a published contract — deleting a tool breaks agents in the wild, and it should require editing a test that says so out loud. Chapter 24 is about doing that gracefully.

Contract tests: quality you can assert#

Some of what chapter 4 argued can simply be enforced.

A tool with no description is a tool the model will misuse. A parameter with no description is a parameter it will guess at. These are not stylistic preferences; they are the difference between a tool being chosen correctly and being chosen at random, and they are trivially checkable.

ledger asserts the same way that every tool carries read-only annotations. When a writing tool arrives, that test fails, and failing is correct — someone should have to think about it.

This class of test scales further than people expect. Token budgets per tool description, naming conventions, required error-message shapes, a cap on the total size of tools/list — all of them are assertions. Chapter 8 turns the size one into a number.

Behaviour, and the messages that go with it#

Ordinary behaviour tests look ordinary:

async def test_find_licences_filters_by_territory(client):
    row = db.one(
        "SELECT title_id, territory FROM licences GROUP BY title_id HAVING COUNT(*) > 3"
    )
    async with client:
        result = await client.call_tool(
            "find_licences",
            {"title_id": row["title_id"], "territory": row["territory"]},
        )
    assert result.data
    assert {r["territory"] for r in result.data} == {row["territory"]}

Note that the test derives its inputs from the fixture rather than hard-coding identifiers. Hard-coded ids rot the first time the generator changes; a query that asks for "a title with more than three licences" keeps meaning what it meant.

The less ordinary tests are the ones about error text:

with pytest.raises(ToolError, match="search_titles"):
    await client.call_tool("get_title", {"title_id": "T-nope"})

That assertion is not about the string. It is about the error naming a recovery. Chapter 4 argued that failure text is a message to the model; this is how you stop that argument decaying into Invalid input six months later.

Pinning what is deliberately wrong#

find_licences returns every row it finds, with no limit and no total. That is a flaw, it is on purpose, and chapter 8 needs it to still be there.

async def test_find_licences_returns_everything_it_finds(client):
    """Deliberately unbounded. When this test starts failing, it is because
    chapter 10 has landed — update it there, not before."""

This is an unusual test to write and a useful habit to have. A known limitation with a test on it is a documented decision. A known limitation with nothing on it is something that will be helpfully fixed by a contributor who does not know why it is there, and the fix will silently invalidate a measurement three chapters later.

The packaging test#

Everything above talks to the server in-process, which proves the logic and nothing about whether it starts. One test spawns it as a real subprocess over stdio:

It is the slowest test in the suite by an order of magnitude and it is worth every millisecond, because it fails on things nothing else can see: a broken console script, an import that only works from the project root, a dependency missing from pyproject.toml that happens to be installed in your environment. Those failures otherwise surface in a reader's editor, as a server that does not appear.

Golden transcripts#

There is one more form of test in this repository and it does not look like a test. code/labs/wire/capture.sh sends a request per method and commits the responses. Re-run it after any change and read the diff.

Two chapters ago that diff did real work: adding a Literal to one parameter changed 35 lines of captured JSON, and the schema the model sees changed with it. No assertion would have told you as much as looking at it.

Use golden files where the interesting question is what does this look like now rather than is this still true. Schemas, error shapes and protocol envelopes all qualify. Keep them in version control and read the diffs; a golden file nobody reads is just a slow way to accept any change.

What none of this tests#

Whether a model can actually use your server.

Every test here is about correctness and contract. None of them tells you that a model picks search_titles before get_title, or that it narrows by territory instead of asking for all 180 licences, or that it recovers from an error the way the message intended. Those are real questions and they need a model to answer.

They are also expensive, slow and noisy, which is why they belong in a separate suite run deliberately rather than on every commit. Chapter 25 builds that suite: task-level evaluations with a regression harness and cost budgets. The division of labour is the point — everything checkable without a model should be checked without one, so that the expensive suite is small enough to actually run.

Checkpoint#

Part 1 is done. ledger has tools, resources and prompts, it runs on both transports, and twenty-four tests hold it in place in under two seconds.

It is also, measured honestly, a server that will fail the first time someone asks it a reasonable question about a popular title. Part 2 changes point of view — from what your server does to what it costs — and it starts by putting a number on that failure.
