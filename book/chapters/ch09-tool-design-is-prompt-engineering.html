Part 2 — The client's point of view · Chapter 9

Tool design is prompt engineering

Naming, description budgets, determinism, idempotency, and designing a tool a model can recover from.

Status draftProtocol 2026-07-28Code git checkout ch09-tool-design

Chapter 8 priced ledger's surface at about 1,435 tokens. This chapter is about spending them well, and the framing that makes that possible is uncomfortable but exact: every one of those tokens is prompt text you wrote, in a prompt you will never read, for a decision you will not see being made.

Nobody reviews tool descriptions the way they review prompts. They should.

How the choice actually happens#

When a user asks "what have we sold in Germany?", the model does not execute a decision tree. It has your tool names and descriptions in context alongside the question, and it produces a call. The inputs to that are: the names as a set, the first line of each description, the parameter names and their descriptions, the schema, and whatever your instructions block established about vocabulary.

Three failures follow, and they are worth naming separately because they have different fixes.

Wrong tool. Two tools are close enough that either seems plausible. The fix is names and first lines that partition the space — not longer descriptions.

Right tool, wrong arguments. The model picks find_licences and omits territory because nothing suggested it mattered. The fix is parameter descriptions that say what happens if you leave this out, and schemas that make the cheap path the easy one.

Right call, no recovery. The call fails or returns nothing and the model does not know what to try next. The fix is error text, which chapter 4 covered, and it is worth re-reading through this lens: an error message is a description that only appears when the model is already confused.

Names are read as a set#

A model does not evaluate find_licences in isolation. It sees four names together and infers a structure from them. search_titles, get_title, find_licences, licence_detail implies: search to find identifiers, get for detail, two entities, licences hang off titles. That inference is free and it is right.

Now imagine adding get_licence next to licence_detail. The set no longer partitions, and no description makes it recover — the model has to read carefully to distinguish tools that the naming implied were different. In practice it will sometimes read carefully and sometimes not.

ledger now has a test for the mechanical half of this:

assert not b.startswith(a + "_"), f"{b!r} shadows {a!r}"

It will not catch get_licence versus licence_detail. Nothing will, except someone reading the list of names out loud and asking whether a stranger could tell them apart.

Descriptions are decision support, not documentation#

The instinct when writing a description is to describe. The useful move is to help choose:

Documentation instinctDecision support
Returns licences for a title.Licences attached to a title — use after search_titles, and narrow by territory when you only need one market.
Searches the title catalogue.Find titles by name. Use this first — every other tool takes a title_id.
Gets details for a licence.One licence in full, with the agreements above it. Use when a licence id from find_licences needs its terms checked.

Each right-hand version answers when rather than what, and each names the tool that comes before or after it. Sequence information is the single highest-value thing you can put in a description, because it is the thing a model has no other way to learn.

The cost is real but small: those rewrites are eight to fifteen tokens each. Against a 10,800-token result, arguing about fifteen tokens of description is not thrift, it is displacement activity.

Where description length actually hurts

Not in the token count — in the reading. A three-sentence description competing with three other three-sentence descriptions is harder to choose between than four one-liners. Long descriptions are a problem when they make the set harder to scan, which is a different failure from being expensive.

Make the expensive path visible in the schema#

Here is the design flaw chapter 8 measured, stated as a design rule rather than a number. find_licences has an optional territory parameter. Omitting it can return three rows or one hundred and eighty. Nothing in the tool says which.

A model has no way to distinguish a cheap call from an expensive one before making it, so it makes the broad one, because the broad one is more likely to contain the answer. That is not a mistake. Given what it knows, it is correct.

Three levers, in increasing order of effort:

Say it in the parameter description. "Omit for every territory — a widely-licensed title can return well over a hundred rows." One sentence, and now the model is choosing with information.

Make the cheap thing the default. An optional filter with no default invites omission. A limit that defaults to 20 does not.

Refuse, with the number and the lever. "4,182 licences match; narrow by territory or status." The model now knows both the scale of what it asked for and how to ask better — and it costs twelve tokens instead of ten thousand. Chapter 10 builds this.

Determinism and idempotency are promises about your system#

Every ledger tool is annotated readOnlyHint, idempotentHint, destructiveHint: false. Those hints are how a client decides what it may run without asking a human, and what it may safely retry.

Which makes them promises, not descriptions. Chapter 13 will show a broken stream losing an in-flight request that the client must reissue as a new one. If you claimed idempotency and a second execution charges someone twice, that is your bug and it happens at three in the morning.

The honest test is not "does calling this twice return the same value" but "does calling this twice leave the world in the same state". A read is trivially idempotent. A write is idempotent only if you made it so, usually with a key.

One tool or two?#

The recurring design question, and the answer is almost always "one, with a parameter".

Two tools cost two definitions and force a choice the model can get wrong. One tool with a well-typed parameter costs one definition and moves the decision into the schema, where a Literal can enumerate the options and the client can validate before anything runs.

Split when the parameter would change what the tool returns in shape, when different variants need different permissions, or when one variant is destructive and the other is not — that last one because the annotations differ, and a single tool cannot be honestly annotated for both.

What this cannot fix#

Everything above assumes a surface small enough that a model can read all of it and choose well. Below roughly a dozen tools, careful description writing is genuinely most of the battle.

Above that, it stops working. Forty well-written descriptions are still forty descriptions to read before answering, and the failure is no longer that any one of them is bad. That is a structural problem and it needs a structural answer, which is Part 4: shrink the surface, search it instead of loading it, or stop exposing tools altogether.

First, though, the other half of chapter 8's bill. Ten thousand eight hundred tokens for one correct call.
