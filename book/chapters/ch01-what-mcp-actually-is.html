Part 0 — Orientation · Chapter 1

What MCP actually is

Protocol, not framework. Where it sits next to plain function calling and an API gateway — and the honest case against using it.

Status draftProtocol 2026-07-28

Most explanations of the Model Context Protocol start with the USB-C analogy. It is a bad analogy, and it has cost the ecosystem a lot of badly-designed servers. USB-C is a physical standard where correctness is binary: the plug fits or it does not. MCP is a text protocol whose output lands in a language model's context window, where correctness is a spectrum and the failure modes are things like the model chose the wrong tool because two descriptions were ambiguous and one successful call consumed 40% of the window.

So this chapter does something less exciting than an analogy. It says what MCP is, what it replaces, what it costs, and when you should not use it — before the rest of the book commits you to building one.

The problem it solves#

Before MCP, every model host that wanted to reach an external system wrote its own integration: its own tool-definition format, its own auth handling, its own transport, its own idea of what a "resource" was. An integration written for one host did not run in another. The work was N hosts × M systems, and almost all of it was the same work done incompatibly.

MCP makes that N + M. A server exposes capabilities once; any conforming client can use them. That is the whole pitch, and it is a real one — but notice what it is not. It is not a way to make a model better at using your system. It standardises the plumbing, not the judgement. A badly-described tool is exactly as badly-described after you put it behind MCP, and now it is badly-described for everyone.

A protocol, not a framework#

MCP is a JSON-RPC 2.0 message vocabulary plus rules for carrying it over stdio or HTTP. That is the entire specification surface. FastMCP, the official SDKs and every other library in this book are conveniences layered over it: useful, replaceable, and — as chapter 2 demonstrates with real responses — occasionally behind the specification in ways you need to know about.

It helps to place it against the two things people most often confuse it with.

Who defines the tool surface The application, per host The API owner The server, once, for every host

Discovery Compile time Out of band, usually a portal At runtime, in the conversation
Cost model Tokens you control Requests Tokens you mostly do not control

The last two rows are the ones this book is organised around. Discovery happens at runtime, which means your descriptions are read by a model rather than by a developer with time to think. And the reading is paid for in a context window you are not billed for and cannot see. Every design decision in the chapters that follow is downstream of those two facts.

The primitives#

Three things a server exposes, distinguished by who decides to use them.

Tools are model-invoked: the model reads the descriptions and chooses. This is the primitive nearly everyone over-uses, because it is the one that obviously works. Every tool you add is a permanent line item in the context budget of every conversation, whether or not it is called.

Resources are application-invoked: the client decides to load them and addresses them by URI. If a user has a document open, the client can put it in context without the model having to ask. Resources are also how you let a model navigate a large corpus rather than fetch it, which is the whole of chapter 21.

Prompts are user-invoked: templates a person picks deliberately. This is the least-used primitive and the one with the clearest reason to exist — it is where a domain's standard question lives, with the method already correct. Chapter 6 makes the case.

The fourth thing is newer and is not a primitive so much as a shape a result can take. A server that needs more information no longer calls back to the client; it returns a result of type input_required carrying the requests, and the client retries the original call with the answers attached. That is the Multi Round-Trip Request pattern, and it replaces sampling, elicitation and roots-listing as they used to work.

What the 2026-07-28 revision changed#

Specification 2026-07-28

Protocol-level sessions are gone, along with the Mcp-Session-Id header and the initialize handshake. Every request now carries its protocol version and client capabilities in _meta. Servers that need state across calls mint explicit handles and take them back as ordinary tool arguments.

This is the largest break since MCP launched, and it is worth knowing before you read anything else about the protocol. A large fraction of the MCP writing on the internet describes a protocol that no longer exists — not subtly out of date, but describing a handshake that has been deleted. Sessions, initialize, ping, stream resumability and server-initiated sampling are removed or deprecated.

The direction is coherent: the protocol is being made stateless so that servers can be scaled horizontally like any other HTTP service, and the awkward parts — a server calling back into a client mid-request, a stream you were expected to resume — have been replaced with retry-shaped equivalents. Whether your library has caught up is a separate question, and chapter 2 answers it by sending requests rather than reading release notes.

The honest case against it#

Before you build one

If exactly one application will ever call your system, and you control that application, MCP is overhead. Write the function.

The protocol earns its keep when the set of clients is open or unknown: several agents, several teams, or a capability you intend to publish. In exchange you take on a wire format to maintain, a tool contract you can no longer change freely, an authorisation story, a version to declare, and a permanent tax on someone else's context window. Those are real costs and this book keeps naming them rather than mentioning them once in a caveat.

There is also a category error worth heading off early. MCP is not a security boundary, not a rate limiter, not an audit log and not a substitute for an API. It sits in front of your system the way a user interface does, and it hands a language model the keyboard. Everything you would not let an enthusiastic new joiner do unsupervised on day one is something you should think hard about exposing. Chapter 18 is about what goes wrong when people forget this, and the answer is usually worse than they expect.

How this book is organised#

Part 1 gets everyone to a working, tested server in five chapters and then stops. If you have built one already, skim it for chapter 7 — the testing approach everything later depends on — and move on.

Part 2 changes the point of view from yours to the client's, and prices what you have built. Part 3 is scale: statelessness, failure, cost, identity and security, and it is the longest part of the book. Part 4 is the context problem — progressive disclosure, filtering tool results with jq, and code mode — which is where a server stops being a demo. Part 5 is shipping.

Everything is built against one running server, ledger, over a synthetic media rights catalogue: titles, licences, territories, windows and a corpus of nested agreements. It is a good teaching domain because the problems arrive honestly. One title in the catalogue carries 180 licences across 33 territories, and the obvious tool returns all of them. You will meet that title repeatedly.

Every chapter that changes the server names a tag, so you can check out the code exactly as it stood at the end of it. Every claim about the protocol links to the specification, and every number was measured on the code in this repository rather than taken from a blog post. Where the two disagree — and they do — the chapter says so.
