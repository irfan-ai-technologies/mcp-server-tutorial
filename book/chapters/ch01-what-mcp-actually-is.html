Part 0 — Orientation · Chapter 1

What MCP actually is

Protocol, not framework. Where it sits next to plain function calling and an API gateway — and the honest case against using it.

Status draftProtocol 2026-07-28

Most explanations of the Model Context Protocol start with the USB-C analogy. It is a bad analogy, and it has cost the ecosystem a lot of badly-designed servers. USB-C is a physical standard where correctness is binary: the plug fits or it does not. MCP is a text protocol whose output lands in a language model's context window, where correctness is a spectrum and the failure modes are things like the model chose the wrong tool because your description was ambiguous and one successful call consumed 40% of the window.

So this chapter does something less exciting than an analogy. It says exactly what MCP is, what it replaces, what it costs, and when you should not use it — before the rest of the book commits you to building one.

The problem it solves#

Before MCP, every model host that wanted to reach an external system wrote its own integration: its own tool-definition format, its own auth handling, its own transport, its own idea of what a "resource" was. An integration written for one host did not run in another. The work was N hosts × M systems, and almost all of it was the same work done incompatibly.

MCP makes that N + M. A server exposes capabilities once; any conforming client can use them. That is the whole pitch, and it is a real one — but notice what it is not. It is not a way to make a model better at using your system. It standardises the plumbing, not the judgement.

A protocol, not a framework#

MCP is a JSON-RPC 2.0 message vocabulary plus rules for carrying it over stdio or HTTP. That is the entire specification surface. FastMCP, the official SDKs and every other library you will meet in this book are conveniences layered over it: useful, replaceable, and occasionally hiding something you need to see.

It helps to place it against the two things people most often confuse it with.

ConcernPlain function callingAPI gatewayMCP
Who defines the tool surface The application, per host The API owner The server, once, for every host
Consumer One model, one app Any HTTP client Any conforming MCP client
Optimised for Whatever you write Machines with documentation A model reading schemas at inference time
Cost model Tokens you control Requests Tokens you mostly do not control

That last row is the one this book is organised around. Your tool names, descriptions and schemas are loaded into a context window you are not paying for and cannot see. Every design decision in the chapters that follow is downstream of that fact.

The primitives#

Three things a server can expose, and one thing it can now hand back mid-request.

Tools are model-invoked actions — the primitive nearly everyone over-uses. Resources are application-controlled context the client can read by URI, which makes them the right home for anything a model should be able to navigate rather than fetch wholesale. Prompts are user-invoked templates, the least-used primitive and the one with the clearest reason to exist once you see it. Chapters 4 through 6 take one each.

The fourth thing is newer: a result can now come back as input_required, carrying requests for information the server needs before it can finish. That replaces the old model of servers making requests back at clients, and it changes how you design anything interactive.

What the 2026-07-28 revision changed#

Specification 2026-07-28

Protocol-level sessions are gone, along with the Mcp-Session-Id header and the initialize handshake. Every request now carries its protocol version and client capabilities in _meta. Servers that need state across calls mint explicit handles and take them back as ordinary tool arguments.

This is the largest break since MCP launched, and it is worth knowing before you read anything else about the protocol: a large fraction of the MCP writing on the internet now describes a protocol that no longer exists. Sessions, initialize, ping, stream resumability, and server-initiated sampling calls are either removed or deprecated. Chapter 2 reads the current wire format directly so you can tell the difference yourself.

The honest case against it#

Before you build one

If exactly one application will ever call your system, and you control that application, MCP is overhead. Write the function.

The protocol earns its keep when the set of clients is open or unknown — several agents, several teams, or a capability you intend to publish. It costs you a wire format to maintain, a tool contract you can no longer change freely, an auth story, and a permanent tax on someone else's context window. Those are real costs and this book will keep naming them.

There is also a category error worth heading off: MCP is not a security boundary, not a rate limiter, and not a substitute for an API. It sits in front of your system the way a UI does. Chapter 18 is about what goes wrong when people forget that.

What this book assumes#

That you write Python, have shipped something with async and HTTP in it, and have opinions about retries. Part 1 gets everyone to a working, tested server in five chapters and then stops; the budget is spent on Parts 3 and 4, where the interesting failures are.

Everything is built against one running project — ledger, an MCP server over a media rights catalogue — which grows chapter by chapter. Every chapter that changes it names the tag you can check out to see the code exactly as it stood there.
